# ADR 0013: `--overwrite` は既存ノートを名前維持で置き換える

- Status: Accepted
- Date: 2026-08-30
- Deciders: Project owner (ttk1010), Lead Software Engineer (Claude Code)

## Context

`--overwrite` は「同じ source を作り直す」意図だが、書き込み先ファイル名は毎回 `slugify_title(ko.short_title or ko.title)` から決まる。`short_title` は LLM 生成で再生成のたびに揺れるため、名前が変わると `resolve_target` が別パスを返し、`overwrite=True` でも旧ファイルに触れず **ノートが二重化**する。イラストも同様に孤児 PNG が残る。さらに `find_existing` は最初の名前順一致を返すため、以降の冪等判定が古い方を拾い続けることがあった（Issue #39, GH #70）。

## Decision

### 案A（名前維持）を採用する

`overwrite` 時は、同一 source の既存ノートを解決し、その **既存ファイル名（stem）をノート・イラスト両方の書き込み先に固定** する。これにより1つの source に対しノート1つ・イラスト1つだけが残り、Obsidian の `[[リンク]]` と画像埋め込みが壊れない（Knowledge First）。案B（改名＋旧ファイル削除）はタイトルを最新化できるが他ノートからのリンクが切れ、削除を伴うため事故時の影響が大きく不採用。

### short_title の改善はログのみ（名前据え置き）

再生成で改善された short_title があっても **ファイル名は据え置き**、差分を INFO ログで通知する（本文の `title` は更新される。据え置くのはファイル名のみ）。ユーザーが必要と判断すれば手動改名できる。

### 二重化した既存 Vault は手作業で掃除

既に二重化した Vault を掃除する専用コマンドは作らない（手作業で十分）。ただし `find_existing` が複数一致を検出したら **警告ログ** を出し、どれを使ったかを知らせる（掃除判断の材料）。

### 解決ロジックは再利用可能な形に切り出す（#29 とは今は結合しない）

上書き対象の解決を `VaultWriter.pinned_stem(ko, *, overwrite)` に集約する。Issue #29（既存ノートの自然言語リファインメント／イラストのみ再生成, #54）が着手時に同じ「既存ファイルを特定して同じパスへ書く」土台を再利用できるが、未着手の #29 に合わせた共通部品化は今は行わない（早すぎる抽象化を避ける）。

## Consequences

- `--overwrite` が「再生成」ではなく **置き換え** として振る舞う。二重ノート・孤児 PNG を新規に作らない。
- 冪等性が安定：同一 source に対し常に同じ既存ノートを対象にする。
- `pinned_stem` は overwrite かつ既存ありのときのみ stem を返す。新規生成・非 overwrite は従来どおり short_title 由来の名前。
- パイプライン共通の `_finalize` が stem を解決し、ノート／イラスト両writerへ渡す（digest 経路にも自動適用）。
- 既存の重複は自動削除しない（ユーザーが手作業で整理）。複数一致時は警告で気づける。

## Alternatives considered

- **案B（改名＋旧削除）**：タイトル最新化と引き換えにリンク切れ・削除事故のリスク。不採用。
- **掃除コマンドの追加**：便利だが現状の重複はごく少数で手作業で足りる。過剰実装として見送り。
- **#29 用に共通部品を先に設計**：二度書きは避けられるが未確定要件への早すぎる抽象化。`pinned_stem` に切り出すに留め、#29 着手時に再利用。
